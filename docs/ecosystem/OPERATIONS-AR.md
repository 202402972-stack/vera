# تشغيل VÉRA ومراجعة الإطلاق

الإصدار يعمل بخدمة واحدة وNode 24 وSQLite، وفرع التنفيذ `codex/vera-ecosystem`. لا نشر أو دمج أجري في هذه الجلسة. صور وفحوص الجلسة محلية، ولا تثبت موافقة مزود الدفع أو أداء الإنتاج عند p75. إعداد دومينات التجار وشهادات HTTPS ومسار Cloudflare موضح في [DOMAINS-AR.md](DOMAINS-AR.md)، ويحتاج حساب مزود خارجي قبل تفعيله حيًا.

## التشغيل المحلي

```bash
npm ci
cp .env.example .env
# PUBLIC_URL=http://localhost:3000, PORT=3001, DATA_DIR=./data
npm run dev
```

للخادم المبني: `npm run build` ثم `PUBLIC_URL=http://localhost:3001 npm start`، وتفتح `http://localhost:3001`. صفحة `/api/health` تفحص SQLite. `npm run lint` و`npm test` للفحوص، وبعد البناء `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:platform:e2e` في البيئة الحالية. على جهاز آخر يمكن `npx playwright install chromium` واستخدام المتصفح الافتراضي. اختبارات المتصفح تنشئ قواعد مؤقتة وحسابات fixtures؛ لا تُضاف حسابات تجريبية إلى بيانات التشغيل.

Google مطلوب للدخول الحقيقي: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `PUBLIC_URL` وcallback `/api/platform/auth/callback` حسب [دليل التكاملات](../INTEGRATIONS.md)، و`OWNER_EMAILS` للبريد المتحقق. لا يوجد تجاوز دخول تجريبي في خادم التشغيل.

## البنية والحدود

- `/workspace` قائمة المتاجر؛ `/workspace/new` مسودة الإنشاء؛ `/workspace/import` الاستيراد؛ `/workspace/stores/:id/:section` إدارة المتجر؛ `/owner/:section` إدارة المنصة.
- المسارات القديمة `/s/:slug/admin` وكلمات مرورها محفوظة. الجسر الجديد يصدر جلسة محددة بمتجر وحساب؛ خروج الحساب يبطل جلساته الصادرة دون إبطال جلسات كلمة المرور الأخرى.
- المتاجر القديمة تهاجر إلى `published` دون تعديل منتجاتها أو طلباتها؛ الجديدة `draft`. النشر منفصل عن التجربة والاشتراك. المراجعة الخاصة قراءة فقط، تتطلب حساب المالك، وتمنع الفهرسة.
- مخطط قاعدة البيانات يضاف عند بدء الخدمة. سجل `platform_schema_migrations` يثبت تحميل المخططات بنجاح. لا إسقاط جداول ولا migration في build.
- لا تضف replica ثانية. عملية الاستيراد داخل الخدمة، مع SQLite leases واستئناف وقاعدة ربط تمنع التكرار. عاملان كحد أقصى، وعملية نشطة واحدة لكل حساب. لا مزامنة دورية ولا تخزين موزع.
- الحدود: 500 منتج، 40 متغيرًا، 3 محاور خيارات، 12 صورة لكل منتج، 2000 صورة تحميل لكل مهمة، 500 MB تحميل إجمالي، 10 MB للملف/الصورة، و40 مليون بكسل للفك. التصوير يعاد ترميزه WebP محليًا. سقف صفحات قراءة Shopify/API هو 1000، مع توقف عند سقف المنتجات. fallback عام لا يتجاوز 10 sitemaps و50 صفحة مرشحة.
- SafeFetch يرفض الوجهات الخاصة والmetadata وuserinfo والمنافذ غير 80/443، يعيد فحص كل redirect، ويحصر الوقت والنوع والحجم. الاتصال المباشر يثبت DNS، وفي هذه البيئة يستخدم proxy الذي يطبق سياسة الشبكة. يجب أن تكون سياسة egress للإنتاج مستقلة وقادرة على رفض العناوين الداخلية أيضًا.
- 429/502/503/504 تؤجل المهمة بحسب Retry-After/backoff بثلاث محاولات تلقائية كحد أقصى. إعادة المحاولة اليدوية تعيد الفاشل فقط. الإلغاء يحتفظ بالتقرير والمنتجات المعتمدة؛ لا يحذف عمل التاجر. الملفات المؤقتة 7 أيام، والتقارير النهائية 30 يومًا؛ خرائط مصدر المنتجات تبقى. نواقص العملة والمخزون لا تُخمّن.
- المنتجات المستوردة مسودات. مراجعة كل سعر ومخزون وصورة مطلوبة؛ لا يمكن اعتماد عملة مصدر مختلفة عن عملة المتجر دون مراجعة صريحة. العملاء والطلبات وكلمات المرور والدفع والاشتراكات لا تُنقل.

## اتصالات رسمية

Shopify: تطبيق OAuth مع `VERA_SHOPIFY_CLIENT_ID`, `VERA_SHOPIFY_CLIENT_SECRET`، `PUBLIC_URL` HTTPS وcallback `/api/platform/import-connections/shopify/callback`. scopes: `read_products,read_inventory,read_locations`؛ API `2026-10`. بعد الربط اختر موقع المخزون. الأسعار بعملة shop؛ نقص location أو stock يبقى يحتاج مراجعة. توجد صلاحية انتهاء token وفصل يمسح السر، لكن إعادة الربط مطلوبة بعد انتهاء access token، دون ادعاء refresh غير منفذ.

WooCommerce: أصل HTTPS ومفاتيح `ck_`/`cs_` بصلاحية **Read** من مالك المتجر. السر لا يرجع للواجهة ويخزن AES-256-GCM. اختيار Read يُضبط في Woo نفسه؛ المصدر قد لا يكشف صلاحية المفتاح عبر API. العملة تؤكدها عند غيابها في product API. المنتجات grouped/external/subscription والرقمية تحتاج بديلًا ومراجعة؛ لا تحويل صامت.

الشبكة السحابية قد تمنع نطاق مصدر غير مسموح. يلزم السماح بنطاق المصدر ونطاقات صوره لدى مسؤول البيئة. CSV والأجزاء المستقلة تظل قابلة للتنفيذ. لا تستخدم تعطيل TLS أو عناوين داخلية لتجاوز الحجب.

## التسعير

أسعار عرض USD/EGP من owner/settings مستقلة عن التحصيل. لا سعر EGP افتراضيًا بلا اعتماد المالك. checkout يرسل معرّف خطة معتمدة؛ snapshots تشمل المبلغ والعملة والمرجع والتكاملات. الخطة الجديدة إصدار جديد؛ callbacks تراجع snapshot الطلب/الاشتراك القديم. الاشتراكات القديمة التي لم يكن لها snapshot تثبت على إعداد المزود الموجود عند الترقية؛ يجب مطابقة ذلك الإعداد مع العقود القديمة قبل الإطلاق، لأن البرنامج لا يستطيع استنتاج أسعار تاريخية مفقودة.

عملة بيع التاجر تغيّر من Financial settings بمراجعة أثر وخيار الاحتفاظ بالأرقام أو معدل إعادة تسعير صريح. الطلبات السابقة لا تتغير. عرض سعر للمشتري بعملة أخرى يستخدم خدمة rates الموجودة في GALA؛ لا يغير عملة التحصيل.

## Flags والتراجع

من owner/settings: workspace، importCsv، importUrl، providerConnectors، displayPricing. ويمكن فرض التعطيل من البيئة:

```dotenv
VERA_FEATURE_WORKSPACE=0
VERA_FEATURE_IMPORT_CSV=0
VERA_FEATURE_IMPORT_URL=0
VERA_FEATURE_PROVIDER_CONNECTORS=0
VERA_FEATURE_DISPLAY_PRICING=0
```

تعطيل workspace يعيد أزرار دخول المتجر إلى المسار القديم؛ الروابط الجديدة تبقى للمتاجر الحالية. تعطيل import/connector يمنع الإنشاء/الربط الجديد، ويبقي التقارير والمهام الموجودة واستكمالها. لا حذف منتجات مستوردة عند rollback. تراجع الواجهة/flags أولًا؛ الرجوع إلى binary أقدم يحتاج اختبار توافق المخطط والبيانات المضافة.

## النسخ الاحتياطي والاستعادة

```bash
DATA_DIR=/data node scripts/backup.js /tmp/vera-backup-YYYY-MM-DD
node scripts/verify-backup.js /tmp/vera-backup-YYYY-MM-DD
```

النسخة تشمل snapshot SQLite متسقة أثناء WAL وuploads و`.encryption-key`. تحقق الاستعادة يستخدم مجلدًا مؤقتًا، يراجع integrity والأسرار المشفرة ويقلع التطبيق من النسخة، دون كتابة على الأصل. لخدمة إنتاج: أوقف الكتابة قبل استبدال **كامل** DATA_DIR، احتفظ بالنسخة السابقة، ثم أعد التشغيل وافحص الملكية والصور والطلبات والدفع. انقل النسخ إلى مخزن خاص خارج السيرفر. uploads تُنسخ بعد snapshot؛ لا تحذف ملفات موجودة أثناء النسخ. التنظيف الحالي لا يحذف uploads المنشورة.

## سجل الإطلاق: شروط غير محسومة

| الشرط                              | الدليل/الحالة                                                             | المسؤول المطلوب |
| ---------------------------------- | ------------------------------------------------------------------------- | --------------- |
| lint/build/tests وصور محلية        | سجل التنفيذ وتقرير الصور                                                  | منفذ الفرع      |
| volume دائم وreplica واحدة         | إعداد repo موجود؛ النشر الفعلي غير مختبر                                  | مشغل Railway    |
| HTTPS/Google/owner                 | لا credentials فعلية في الجلسة                                            | مالك المنصة     |
| Paymob أو Stripe حقيقي وخطة معتمدة | منطق snapshots وفحوص محلية؛ عملية المزود الحية غير مثبتة                  | مالك حساب الدفع |
| Shopify/Woo + مخزون موقع           | endpoints وواجهة جاهزان؛ لا حساب مصدر متاح للاختبار الحي                  | مالك المصدر     |
| backup خارج السيرفر                | استعادة محلية ناجحة؛ التخزين الخارجي والجدولة غير مضبوطة                  | مشغل الخدمة     |
| مراقبة وتنبيهات                    | health + owner imports؛ ربط تنبيهات uptime/error/latency/disk/queue مطلوب | مشغل الخدمة     |
| سياسات ودعم حقيقي                  | readiness يطلب المراجعة؛ محتوى التاجر الفعلي مطلوب                        | التاجر          |

راقب `/api/health` خارجيًا، 5xx وزمن الطلبات، حجم `/data` وuploads، وعدد المهام ذات lease منتهية/failed/partial من owner imports. إنذار أولي: health يفشل مرتين، مساحة القرص الحرة أقل من 20%، أقدم مهمة نشطة بلا تقدم 10 دقائق، أو نمو خطأ الدفع. يجب تحديد جهة تنبيه ومسؤول قبل التجار الحقيقيين. أهداف LCP/INP/CLS الواردة في الخطة تحتاج قياسًا ميدانيًا؛ لا تُعرض هنا كنتائج محققة.

## أدلة الترقية والفحص

`node scripts/verify-upgrade.mjs a4e0279` ينشئ نسخة مؤقتة من كود master السابق، يولد بيانات منتج وطلب وكلمة مرور وحالة إيقاف/انتهاء، ثم يقلع الكود الحالي على نفس البيانات ويقارنها. النتيجة المحلية: 4 منتجات وطلب واحد وكلمة المرور وحالات الإيقاف/الانتهاء محفوظة، و4 migrations مسجلة. لا كتابة على DATA_DIR الحقيقي.

يمكن خفض حدود النقل من owner/settings حتى السقوف السابقة؛ لا يمكن رفعها عن الحدود الصلبة. تُحسب الصور والمحاولات المحملة ضمن ميزانية المهمة حتى عند فشل معالجة صورة. DNS/timeouts وأخطاء الشبكة المؤقتة تستخدم backoff المحدود. صور المراجعة لها cache خاص 60 ثانية حتى 100 thumbnail، وتزامن أقصى 4 للمنصة و2 للحساب؛ لا تُستخدم كبديل عن الصور المنسوخة محليًا عند الاعتماد.

[سجل التنفيذ](EXECUTION-AR.md) و[تقرير الصور](VISUAL-REVIEW-AR.html) يوضحان الدليل لكل تذكرة. اختبارات المتجر القديم: `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium PLAYWRIGHT_SKIP_FONT_READY=1 npm run test:e2e`. يستخدم متغير انتظار الخطوط في التصوير فقط داخل هذه البيئة، ولا يعطل فحوص الوظائف أو المقاسات.

لالتقاط صور إضافية لخطوات القوالب وقائمة المنتجات والمحرر على الهاتف: بعد build شغّل `node tests/platform-browser/server.js` في terminal مستقلة (قاعدة مؤقتة على 3300)، ثم `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium node scripts/review-ecosystem.mjs` وأوقف خادم fixtures بعد التصوير. لا يستخدم السكربت حسابات إنتاج.

`/sitemap.xml` فهرس المتاجر المنشورة المتاحة فقط (حتى 10000 متجر)، وكل متجر له `/s/:slug/sitemap.xml` بمنتجاته المنشورة. تُستبعد المسودات والمعاينات؛ `robots.txt` وcanonical وnoindex مضافة للصفحات المناسبة، والمعاينة الخاصة ترسل `private,no-store`. الحاجة إلى فهرس أكثر من 10000 متجر تتطلب pagination للفهرس قبل ذلك الحجم.
